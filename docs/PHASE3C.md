## Contract method mappings

| Workflow | Actual method / source |
| --- | --- |
| Discovery | `TrustEscrow.nextProjectId()`, `projects(uint256)`, `milestones(uint256,uint256)` |
| Create | `createProject(address,uint256[],uint64[],bytes32)`; created ID from the confirmed `ProjectCreated` receipt event |
| Token balance/allowance | `MockUSD.balanceOf(address)`, `allowance(address,address)`, `decimals()`, `symbol()` |
| Exact token approval | `MockUSD.approve(TrustEscrow address, project.total)` |
| Funding | `TrustEscrow.fundProject(uint256)` |
| Acceptance | `acceptProject(uint256)` |
| Submission | `submitMilestone(uint256,uint256,bytes32)` |
| Approval/payment | `approveMilestone(uint256,uint256)` |
| Timeout release | `releaseAfterReviewTimeout(uint256,uint256)` |
| Actual payout allocations | `MilestoneSettled`: gross, freelancer gross/net, client refund, service fee |
| Treasury fee receipt | `ProtocolTreasury.totalServiceFeesReceived()` plus matching settlement event fee; cumulative revenue is explicitly labeled |
| Event history | Existing escrow events and wallet-to-escrow MockUSD `Approval` events, never invented transaction records |

Project IDs are zero-based uint256 values held as bigint and canonical decimal URL strings (`/projects/0` is valid). Milestone indices are zero-based; the contract's uint8 count/current index is safely represented as a number and converted to bigint for calls. Solidity getter tuples are mapped in their actual ABI order:

```text
Project: client, freelancer, metadataHash, total, escrowRemaining, acceptBy,
         feeBps, currentMilestone, milestoneCount, state
Milestone: amount, dueAt, submittedAt, reviewEnd, evidenceHash, state
Project states: 0 UNFUNDED, 1 FUNDED, 2 ACTIVE, 3 COMPLETED, 4 CLOSED
Milestone states: 0 PENDING, 1 SUBMITTED, 2 DISPUTED, 3 SETTLED
```

## Discovery and real data boundaries

When a wallet is connected, dashboard/projects/transactions switch to chain-backed views. Invalid networks/manifests or failed reads produce unavailable/error states rather than substituting sample projects. Disconnected users retain the explicitly labeled preview and its original `tl-*` detail routes. Explicit preview detail routes remain read-only and labeled even if a wallet is connected. Disputes/juror routes remain preview-only until later approval.

Discovery reads at most 20 candidate IDs per page, newest first, with four candidate reads in flight. It filters by client/freelancer address and reads at most five milestones per matching project. Pages share a pinned block snapshot; Refresh starts from current chain state. There is no project-discovery log scan or unlimited loop to nextProjectId. A matching wallet's oldest projects may require several explicit Load earlier projects operations. Dashboard counts and escrow totals are clearly limited to loaded pages; pending milestone actions derive from the acting role and current contract state/deadlines. Recently confirmed session transactions are shown separately.

This bounded counter pagination has O(total protocol projects) worst-case discovery cost across all user-requested pages. It is appropriate for local development, not a scalable substitute for an indexed wallet-project lookup. A future authenticated/event-indexed backend needs separate approval.

Queries include account, chain and deployment identity. Account/network changes hide stale financial values and fetch the new wallet's data. Project details poll every 10 seconds; lists can be refreshed and are invalidated after confirmations. Shared deployment read validation has a 30-second stale window and 30-second polling, avoiding observer-mount refetch loops. **Every write still performs fresh validation**, independently of this read cache.

## Creation and metadata

The form validates a real nonzero EVM address (including checksum rules), rejects a freelancer equal to the acting client, requires 1–5 named milestones, positive six-decimal mUSD amounts and a uint256-safe total. UTC dates must exist, increase strictly and fit uint64. The first deadline is strictly later than the latest chain timestamp plus seven days. Offline draft review uses local time but cannot submit; connected writes revalidate against chain time.

Creation stores the contract-supported freelancer, amounts, deadlines and a nonzero metadata hash. Titles, long scope text and milestone descriptions are **session-only**. The frontend computes a deterministic Keccak-256 hash of versioned JSON containing those descriptions, amount strings and deadline strings. The text itself is not sent to the contract and is not saved to a server. A hash is not encrypted storage; do not enter confidential deliverables or personal information.

After confirmation the app decodes ProjectCreated from the actual escrow receipt, checks the emitter and client, stores descriptive metadata in memory under the deployment/project/hash, and navigates to the receipt-derived ID. It never predicts an ID from nextProjectId or treats simulation's return value as the created ID. Creation is distinct from token approval, funding and acceptance. Refreshing clears metadata; the same project then appears as `Project #<id>` with actual participants/amounts/deadlines. Metadata may also be unavailable after changing the verification snapshot or opening another browser.

Review dialogs bind to the wallet, deployment, project and milestone they displayed. Account/deployment or current-milestone changes invalidate that review. The fresh preflight rejects a different deployment snapshot or milestone index instead of silently sending to newly exported addresses or settling a subsequent milestone. Return to editing/review after such a change.

## Creation bug fix: zero gas balance and hidden feedback

The reported client had zero local ETH and zero mUSD. On the running chain, a read-only createProject simulation succeeded with a sample valid one-milestone draft; gas estimation returned 212,411 units. Creation itself transfers no mUSD. The gas preflight correctly rejected a zero-ETH wallet before eth_sendTransaction, so MetaMask had no transaction to confirm.

The visible failure was in ProjectForm: it closed the review dialog before preflight and placed TransactionFeedback above the long form. Focus returned to the Review draft control lower down the page; the gas error was outside the visible area. A regression against the original build reproduced the closed dialog with the actual insufficient-ETH message above the form. There was also an untracked getBlock/validation await before transaction tracking began, and early returns for unavailable context/busy state had no explanation.

The corrected execution path is: Review draft validates and snapshots the draft/metadata and actor/deployment → Create starts synchronous duplicate protection → the existing transaction controller immediately publishes validation → fresh RPC/wallet/deployment checks → fresh chain-time validation → actual createProject simulation and gas/balance preflight → injected wallet write → submitted hash and receipt wait → actual ProjectCreated log extraction → metadata saved in memory → success toast and navigation to the receipt-derived ID. The ABI remains createProject(address,uint256[],uint64[],bytes32).

The dialog stays open during signing, confirmation and failures. It scrolls its live feedback into view, explains wallet prompts, shows submitted hashes and preserves rejected/reverted/unknown-confirmation distinctions. Form validation and configuration failures are visible; duplicate or unavailable-context attempts no longer silently return. Creation requires local ETH for gas but no token balance or allowance. If creation is confirmed but receipt parsing/navigation fails, another creation is disabled and the user is directed to Transactions rather than accidentally creating twice.

Read-only deployment checks confirmed chain 31337 at port 8545, the block-9 anchor, identical repository/frontend manifests, all five runtime hashes and all five compiled/generated ABI hashes. TrustEscrow was 0xCf7Ed3AccA5a467e9e704C703E8D87F634fB0Fc9. The reported wallet's balance was checked directly; the app's existing chain/runtime validations were retained. No funds were transferred, contracts redeployed, or tracked addresses changed during diagnosis.

This fix changes ProjectForm, TransactionFeedback, the existing creation unit/integration tests, test-only wallet/RPC fixtures, a new tests/creation.spec.ts and this guide. Playwright now accepts PLAYWRIGHT_PORT (default 3000) so tests can own port 3001 while a developer keeps their app on port 3000. Production Solidity, escrow methods, token economics and dependencies are unchanged.

## Approval and funding

Only the recorded client sees funding while a project is UNFUNDED and chain time is at or before acceptBy. The acceptance window starts at **creation**, not funding; the earlier preview wording was corrected to match Solidity.

The detail page reads the actual token balance and escrow allowance. An insufficient balance disables approval/funding. When allowance is insufficient, the client reviews an approval for exactly project.total, signs it, waits for a successful receipt and rereads allowance. Approval does not change project funding state. Funding is a separate reviewed transaction transferring the full budget through fundProject. Existing sufficient allowance can be used without another approval. No maximum uint256 approval, auto-mint or automatic deposit is used.

Each write rereads current contract state, checks role/state/deadlines/balance/allowance as appropriate, simulates the actual ABI call, estimates native gas, and verifies account/chain again before wallet submission. A 20% gas-limit buffer and current gas-price estimate detect clearly insufficient local ETH; final wallet fees can still differ, and wallet/RPC errors remain handled. Transactions rejected or reverted are never reported as successful deposits.

## Freelancer delivery and client settlement

Only the named freelancer can accept a FUNDED project through acceptBy inclusive. After acceptance, only the current sequential PENDING milestone may be submitted, through dueAt plus 48 hours inclusive. Submission requires a nonzero bytes32 content hash (0x plus 64 hex digits). Raw deliverables, arbitrary private text, file uploads and public file URLs are not accepted as submission content. Secure file delivery/evidence storage is deferred. The confirmed submittedAt/reviewEnd values are read from escrow; reviewEnd is 72 hours after submission.

Only the client can approve a current SUBMITTED milestone. Solidity permits client approval after reviewEnd as long as it is still submitted; the UI preserves that behavior. The freelancer's timeout-release action appears only when chain time is **strictly greater than** reviewEnd. Both paths settle exactly once through existing contract checks. Frozen/DISPUTED and SETTLED milestones expose neither payment nor submission actions; no dispute-opening action is added.

For normal full payout, serviceFee = floor(amount × feeBps / 10,000) and freelancerNet = amount − serviceFee, entirely with bigint. The page labels this prospective full-payment allocation before approval. A SETTLED milestone is not automatically labeled as a full freelancer payout: refunds/partial arbitration may have occurred externally, so actual allocation comes from MilestoneSettled events. The current cumulative treasury service fees are read separately and never mislabeled as one project's fee alone. Confirmation refreshes project, token and protocol queries.

## Transaction tracking and history

The Phase 3B transaction controller now has a memory-only observer. Account-scoped UI updates remain suppressed after navigation/account changes, while already submitted hashes and eventual receipts stay tracked under their original actor/deployment. One unresolved request per wallet/chain is allowed across page controllers. Unconfirmed hashes retain that lock; the Transactions page can explicitly check a receipt against its original deployment and sender. Reload clears this client-side memory, so on-chain authorization/state checks remain essential and receipts must be checked before retrying an uncertain request.

Submission, confirmation, rejection, preflight failure, mined revert, unknown confirmation, repricing, replacement and cancellation stay distinct. Replacement reason survives an uncertain confirmation so a later receipt check does not label a different replacement as success for the original action. Successful confirmation triggers query invalidation; a refresh error is separate from confirmed execution.

Transaction history displays two explicit sources:

- **This browser session:** in-memory requests with action, phase, actual hash when returned, project/milestone where known, intended token amount, and mined timestamp when obtainable. A token-approval amount is an allowance, not a payment. Failed preflight requests have no fabricated hash.
- **On-chain event history:** confirmed escrow events and this wallet's escrow approvals. Discovery IDs bound the wallet's project filter; Transactions provides Load earlier wallet projects to expand that scope. Event queries use explicit from/to blocks in pages of at most 200 blocks; Load earlier events is required for older history. Deployment start is located with at most 64 historical code lookups between genesis and the verified anchor, avoiding the incorrect assumption that an export made after project activity is the deployment block. Pages over 2,000 logs report a density limitation rather than claiming incomplete results are complete. Timestamp lookup is bounded to 30 distinct blocks per page, four at a time; remaining rows show a block number.

The two sources can refer to the same transaction and are not added together for balances or payment totals. Hash-copy controls are provided; no invented public explorer URL is used for Hardhat. No database, permanent client history, event indexer or backend API is introduced. Unknown/older settlement allocations remain explicitly unloaded until their event page is read.

## Known limitations and Phase 3D dependencies

- Metadata and client request history are memory-only. Different browsers and re-exported verification snapshots may not retain descriptions. Hashes alone do not recover or encrypt the original metadata.
- Discovery is paginated by protocol IDs and totals are for loaded pages. Event history is bounded and may require older pages; it is not a durable/reorg-aware indexer. Historical state support is required to locate deployment start.
- Single local confirmation is the existing development policy. State can change between simulation and mining; contract reverts are handled, and frontend checks are never the authorization boundary. Session duplicate protection does not survive a full page reload; check receipts before resubmission.
- Token/native provisioning is external and controlled. Gas estimates are not a promise of the final wallet fee. No automatic minting or transfer from another user's account is implemented.
- Refund interfaces remain available on the contracts but refund UI is deferred. Disputes, juror staking/voting/claims and treasury administration are not implemented in this phase. No confidential file delivery, evidence access control, backend persistence or authentication session exists.
- No new Phase 3C manual MetaMask, hardware-wallet, Safari/Firefox, public-chain or audit claim is made. Browser viewport tests use headless Chrome. Prior development-tool audit findings documented in Phase 3A/3B are not silently fixed via dependency upgrades.

After review, Phase 3D can separately integrate dispute/juror workflows, with existing arbitration timing and authorization rules, and later phases can add authenticated metadata/evidence storage and a resilient event index. Do not proceed automatically.
